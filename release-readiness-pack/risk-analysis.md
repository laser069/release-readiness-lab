# Risk Analysis — checkout-api v2.4

Risks found during this review, worst first.

| # | Risk | Severity | Likelihood | Mitigation | Owner |
|---|---|---|---|---|---|
| 1 | `DATABASE_URL`/`REDIS_URL` missing from `k8s/configmap.yaml` — app silently falls back to per-pod in-memory SQLite + local dict cache. At 3 replicas, state doesn't share across pods and is lost on every restart/reschedule. `/health` still returns 200 while this is happening, so nothing pages anyone. | **High** | Certain (confirmed live — see config-verification.md) | Add both vars via a k8s `Secret` before deploy; also make `/health` return non-200 when either dependency is in fallback mode, so probes catch it | Release Owner + SRE/Ops Lead (see ownership.md) |
| 2 | Flask 3.0.2 (the shipped runtime dependency) has a known vulnerability, `PYSEC-2026-2151`, fixed in 3.1.3 — confirmed via `pip-audit` against the actual installed venv | High | Certain (confirmed by scan) | Bump `Flask==3.1.3` in `requirements.txt`, re-run test suite, rebuild image | Release Owner |
| 3 | Health check doesn't fail when dependencies are degraded — `/health` returns `200 healthy` even with both DB and Redis in fallback mode (confirmed live). Readiness/liveness probes in `deployment.yaml` point at this endpoint, so Kubernetes has no way to detect the degraded state via probes | Med | Certain (confirmed live) | Change `/health` to return non-200 (e.g. 503) when `db_status`/`redis_status` are in a `warning_*` state | Release Owner |
| 4 | Mutable image tag (`kalvium/checkout-api:v2.4`) with `imagePullPolicy: IfNotPresent` — no digest pin, so a rebuild under the same tag can silently ship different bits, and rollback-by-tag is ambiguous | Med | Possible | Pin by digest, or switch to `imagePullPolicy: Always` at minimum | SRE/Ops Lead |
| 5 | No `Secret` handling exists anywhere in the manifests — once DB/Redis URLs are added they'd currently have nowhere to go except the plaintext `ConfigMap`, which would expose credentials in cleartext | Med | Certain once #1 is fixed naively | Create a `Secret` alongside the `ConfigMap` fix; wire via `envFrom.secretRef` | SRE/Ops Lead |
| 6 | Rollback plan (this pack's `rollback-plan.md`) is written and command-reviewed but never executed against a live cluster — no kind/minikube/staging cluster was available in this environment | Med | Possible (rollback mechanics untested under real failure conditions) | Run the documented rollback sequence against a staging cluster before this ships to prod | SRE/Ops Lead |
| 7 | Gunicorn runs with default worker/thread settings (1 sync worker per pod) — no `--workers` flag in the Dockerfile CMD, thin concurrency for a "critical" checkout path at only 3 replicas | Low-Med | Possible under load | Set explicit `--workers`/`--threads` tuned to the pod's CPU limit (`500m`) | Release Owner |
| 8 | Dockerfile installs the full `requirements.txt` (including `pytest`, a test-only dependency) into the production image, increasing image size and attack surface for no runtime benefit | Low | Certain | Split into `requirements.txt` (runtime) / `requirements-dev.txt` (test), only install dev deps in CI | Release Owner |
| 9 | Test suite (`test_app.py`) only asserts HTTP status and key presence for `/health`, not the actual `database`/`redis` status values — CI would pass even with both dependencies degraded | Low | Certain | Add a test asserting `checks.database == "connected"` under a configured env, and a separate test for the fallback path | Release Owner |
| 10 | No ownership or on-call assigned anywhere in the repo prior to this pack — an incident during/after deploy would have no clear first responder | Med | Certain (confirmed absent) | Fixed in `ownership.md` in this pack | Release Owner |

Rows 1 and 2 are the release-blocking risks — see readiness-report.md for how they gate the go/no-go call. Rows 3, 5, 6, 10 should be closed before the next release window even if not blocking this one. Rows 4, 7, 8, 9 are backlog-worthy but not urgent.
